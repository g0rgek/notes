Структура данных внутри RDBMS, которые ускоряют чтение, но замедляют запись и расходуют память.
В первом приближении, это KV хранилище, которое позволяет за О(1) найти номер строки в таблице для этого ключа.

# Виды
## Hash индекс
Для оператора =, те поиск по заданному числу.
## BTree
Для оператора =, <, >, IN, BETWEEN, LIKE `foo%`
Отсортированные значения столбца хранятся блоками в сбалансированном дереве
Для PRIMARY KEY по дефолту используется BTREE индекс.

Данные хранятся блоками, чтобы можно было вычитать за раз много. ref указывает на блок со значениями 0-50, 51-100 и тд.
В данном случае, подняли всего 3 страницы.
```
SELECT name FROM users WHERE id = 61;

				       root
		+------|ref|50|ref|100|ref|...|---------+
		|	             |                      |
|ref|15|ref|30|ref|	|ref|65|ref|83|ref|  |ref|115|ref|134|ref|
                      |
                      -----V	leaf
					|56-3|61-10|63-8|
```
## GiST
Геометрическое индексирование (справа, слева, пересекается, содержит и т.д.)
По сути, тоже дерево. Но устроено сложнее. Элементы - это квадраты, которые содержат другие квадраты.
## GIN
Для полнотекстового поиска, работы с массивами (вхождение элемента в массив, пересечение массивов)
## BRIN
Для индексирования столбцов, в которых данные идут последовательно. Например, временные ряды (timeseries). Есть корелляция от данных и того порядка, в котором мы их кладем.
# Селективность
Сколько вернет SELECT - селективность. Чем меньше, тем лучше.
Те нужно ставить индекс на такой столбец, которые больше всех отсекает варианто, например id.
Если селективность слишком большая, то БД может забить на индекс и использовать FULL SCAN таблицы.
# Составной индекс
Это индекс, построенный **по нескольким колонкам в определённом порядке**, например:
```sql
CREATE INDEX idx_orders_user_status ON orders (user_id, status);
```

Такой индекс хранит значения **user_id → status → ссылка на строку**, а порядок колонок в индексе критически важен.

Для индекса `(a, b, c)`:
- отлично работает для:
    - `a`
    - `a AND b`
    - `a AND b AND c`
- **не работает** (или почти бесполезен) для:
    - только `b`
    - только `c`
    - `b AND c` без `a`
Это называется **правило левого префикса**.

Составной индекс эффективен до первого неравенства включительно. Сначала ставим все равенства, потом неравенства.
```sql
users
id name birth_date age
42 John 1985-01-01 34
17 Ivan 1990-07-22 43
89 Ava  1978-11-05 25

CREATE INDEX users_idx ON users (name, birth_date);

SELECT * FROM users WHERE name='Ava'AND birth_date BETWEEN 1978-01-01 AND 1979-01-01; -- effective
```

Если несколько неравенств, то после первого эффективность теряется:
```sql
users
id name birth_date age
42 John 1985-01-01 34
17 Ivan 1990-07-22 43
89 Ava  1978-11-05 25

CREATE INDEX users_idx ON users (name, birth_date, age);

SELECT * FROM users WHERE name='Ava'AND birth_date < '1979-01-01' AND age < 50;
```
## Покрывающий индекс
В индекс можно добавлять столбцы, которые мы селектим в запросе. Тогда запрос не пойдет в таблицу, а заберет все из индекса.
```sql
SELECT y FROM tab WHERE x = 'key';
CREATE INDEX tab_x_y ON tab(x) INCLUDE (y);
```
