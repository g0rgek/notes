# Какие проблемы решает
1. В любой момент времени оборудование или ПО может отказать
2. Может упать pod (когда половина операций с данными уже завершена)
3. Может оборваться сеть между подом и БД, или между двумя инстансами БД
4. Несколько клиентов могут одновременно писать в одну и ту же БД, перетирать изменения друг друга
5. Клиент может прочиать данные, которые были изменены лишь частично
6. Баги из-за гонок данных
# Atomicity
Атомарность позволяет либо выполнить всю работу, либо не выполнять совсем. Главное свойство атомарности - откатываемость (abortability).

Без автомарности и транзакций, на каждую ошибку придется вручную писать логику отката. На каждый запрос нужно писать анти-запрос и кэшировать данные, которые были изменены.
```go
func saveData() {
	saveInDB1()
	if err := saveInDB2(); err != nil{
		rollbackSaveInDB2()
		rollbackSaveInDB1()
	}
	saveInDB3()
	saveInDB4()
	saveInDB5()
}
```

Транзакции делают это за нас:
```go
func saveData() {
	BeginTransaction()
	if err := saveInDB1(); err != nil{
		Rollback()
	}
	saveInDB2()
	saveInDB3()
	saveInDB4()
	Commit()
}
```
# Consistency
Согласованность добавляет ограничения (constraints):
- UNIQUE
- PRIMARY KEY
- REFERENCES (foreign key)
- NOT NULL
- ON DELETE (CASCADE, SET NULL...)

Согласованность это ответственность приложения (разработчик должен прописать все ограничения, чтобы они работали)
## Foreign key
### Плюсы
- гарантирует согласованность
- все нужные проверки берет на себя БД
- структура БД становится более четкой
### Минусы
- оверхед при вставке/редактировании строк
- может усложнить миграции
- блокировки транзакций (особенно при больших нагрузках)
- при работе со связанными таблицами в разном порядке могут возникать дедлоки
# Isolation
Запросы в БД могут выполняться конкурентно, из-за этого может возникнуть состояние гонки. Изоляции транзакций означает, что транзакции не могут получать доступ к одним и тем же записям одновременно.
## Уровни изоляции
- **Read uncommited** работает как **Read commited**.
- При уровне **SERIALIZABLE** блокируется вся таблица для выполнения транзакции.
- При уровне **SERIALIZABLE**, если при изменении порядка выполнения транзакций общий результат тоже изменяется, то часть транзакций откатывается.
## Аномалии

|                 | Грязное чтение             | Неповторяющееся чтение | Фантомное чтение           | Аномалия сериализации |
| --------------- | -------------------------- | ---------------------- | -------------------------- | --------------------- |
| Read uncommited | допускается, но не в PGSQL | возможно               | возможно                   | возможно              |
| Read commited   | невозможно                 | возможно               | возможно                   | возможно              |
| Repeatable read | невозможно                 | невозможно             | допускается, но не в PGSQL | возможно              |
| Serizalizable   | невозможно                 | невозможно             | невозможно                 | невозможно            |
### Грязное чтение
Транзация видит незакомиченное изменени другой транзакции.
```sql
-- Transaction 1                          
UPDATE items SET price = 50 WHERE id = 1;        
-- ROLLBACKS

-- Transaction 2
SELECT id FROM items WHERE price < 30;
-- COMMIT
```
```
Transaciton 1       | Transaction 2
id | price          | id | price
1  | 10 -> 50 -> 10 | 2  | 20
2  | 20             |
3  | 100            |
4  | 200            |
```
Пришли 2 транзакции. Первая транзакция изменила цену товара с 50 до 10. В этот же момент, вторая транзакция запросила все товары с ценой меньше 30. Но после некоторого времени, первая транзация отменилась и вернула цену товара с 50 до 10.
Вторая транзакция получила не все результаты.
### Неповторяющееся чтение
Один и тот же запрос в рамках одной транзакции возвращает разные результаты.
```sql
-- Transaction 1                          
SELECT price FROM items WHERE id=1; -- 10
SELECT price FROM items WHERE id=1; -- 50

-- Transaction 2                          
UPDATE items SET price = 50 WHERE id=1;
-- COMMIT
```
```
Transaciton 1       
id | price          
1  | 10 -> 50
2  | 20             
3  | 100            
4  | 200            
```
### Фантомное чтение
Один и тот же запрос в рамках одной транзакции возвращает разный набор строк.
```sql
-- Transaction 1                          
SELECT id FROM items WHERE price < 30; -- single row
SELECT id FROM items WHERE price < 30; -- two rows

-- Transaction 2                          
UPDATE items SET price = 50 WHERE id=1;
-- COMMIT
```
```
Transaciton 1       
id | price          
1  | 10 -> 50
2  | 20             
3  | 100            
4  | 200            
```
### Аномалия сериализации
Если при изменении порядка выполнения транзакций общий результат тоже изменяется.
На уровне **Serializable**, БД отменит одну из транзакций и закомитит оставшуюся.
```sql
-- Transaction 1                          
SELECT SUM(price) FROM items WHERE category = 1; --30
INSERT INTO items (category, price) VALUES (2, 30);

-- Transaction 2                          
SELECT SUM(price) FROM items WHERE category = 2; --300
INSERT INTO items (category, price) VALUES (1, 300);
-- COMMIT
```
```
tr1->tr2              tr2->tr1
category | price  |   category | price
   1     | 10     |     1      | 10
   1     | 20           1      | 20
   2     | 100          2      | 100     
   2     | 200          2      | 200
   2     | 30           1      | 300
   1     | 330          2      | 330
```
# Durability
Если транзакция закомитилась, то она сохранилась на надежном носителе.
Идеальной надёжности не существует.

Достигается это через:
- Write-ahead log (WAL)
- репликацию
- бекапы
