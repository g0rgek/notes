type hmap struct {
	// Note: the format of the hmap is also encoded in cmd/compile/internal/reflectdata/reflect.go.
	// Make sure this stays in sync with the compiler's definition.
	count     int // # live cells == size of map.  Must be first (used by len() builtin)

If you need to read from and write to map from goroutines, the access must be mediated by some kind of synchronization mechanim.

```go
type bmap struct {
    tophash [bucketCnt]uint8     // HighOrderBits hash для быстрого сравнения
    keys    [bucketCnt]keyType   // Массив ключей
    values  [bucketCnt]valueType // Массив значений
    overflow *bmap               // Указатель на бакет переполнения
}
```
Buckets - массив односвязных списков. 
Порядок итераций по ним не определен: различные реализации могут использовать разные хэш функции, что приведет в иному порядку. Разработчики специально сделали итерацию по массиву бакетов случайной, чтобы разработчики не привязывались к конкретной реализации работы хэшмапы.

Ключ мапы должен быть comparable. Поэтому слайс не может быть ключом мапы.
Структура может быть ключом, пока все поля в ней - comparable.

Нельзя взять указатель на элемент мапы, так как может произойти эвакуация и указатель станет невалидным.

В каждом бакете может хранится не более 8 элементов: 
Машинное слово - 8 байт, поэтому 8 бакетов. 
## Алгоритм чтения
Чтение всегда начинается с рандомного бакета. Так как SEED  для каждой мапы от запуска к запуску меняется, данные по мапе раскладываются рандомно. Поэтому раномный выбор бакета захаркожен в языке, объясняется тем _чтобы программисты не полагались на конкретный порядок значений, так как будущем все может измениться._
НО, `fmt.Println()` выводит мапу в отсортированном по ключу порядке.
### Шаги
0. Если map == nil или пустая - возвращается zerovalue
1. Вычисляется hash для переданного ключа: `hash(1) = 1010101...001`
2. Вычисляем `LowOrderBits` (последние N битов хэша): `LOB = log2(num_buckets)`. 
	LOB отвечает за индекс бакета, в который будет записано значение.
3. Проверяем old buckets - если мапа была эвакуирована
4. Копируем tophash (первый байт) хэша, для проверки наличия ключа в бакете.
5. Проходимся по всем бакетам, сравниваем tophash. Если нашли такой - скорее всего ключ есть в бакете.
6. Проходимся по массиву keys, сравниваем.
7. Если нашли  - возвращаем.
7. Если нет - возвращаем zero value
Полный перебор по слайсу всегда быстрее полного перебора по map, а не в каких-то специальных случаях. Даже без всяких кешей процессора, там же обвязка с рандомизацией. Если бы вопрос был наоборот - бывает ли перебор по слайсу быстрее доступа по ключу к map - и тут уже действительно ответ да в особых случаях, на map меньше 8.
### Сложность (O(1)->O(N))
1. hash(1) - O(1)
2. LOB(hash(1)) - O(1)
3. tophash = hash first byte - O(1)
4. сравниванием tophash - O(8) = O(1)
5. сравниваем keys - O(8) = O(1)
6. Получили значение по такому же индексу, как ключ - O(1)
Итог: O(1)
Всегда ли такая сложность - **НЕТ**. Если LOB сопадет с бакетом, который уже заполнен, то создается еще один бакет. И ссылка на него будет записана в поле `overflow` структуры бакета. В худшем случае, получим O(N).
## Алгоритм записи
Чтобы записать KV в мапу, ключ (K) должен быть [COMPARABLE](1.2%20uncomparable%20types.md). По-простому, для него должен быть определен оператор сравнения `==`. Не все типы являются comparable по той или иной причине.
### Шаги
```go
m := make(map[int]int)
m[1] = 10
```
1. Рассчитываем hash от ключа: `hash(1) = 1010101...001`
2. В какой бакет положить эти kv? Берет LOB (low order bits) от хэша - последние N бит.
	N рассчитывается по формуле: `N = log2(num_buckets) = 3`
	В нашем случае, LOB=001 = 1. Значит индекс бакета в массиве buckets = 1.
3. В массив tophash кладем первый байт хэша. Нужен он для того, чтобы быстро определять есть ли (потенциально) такой kv в этом бакете.
4. В массив keys кладем ключ
5. В массив values кладем значение
### Сложность (O(1) -> O(N))
1. hash(1) - O(1)
2. LOB(hash(1)) - O(1)
3. tophash = hash first byte - O(1)
4. append(tophash) - O(1)
5. append(keys) & append(values) - O(1)
Итог: O(1)
Всегда ли такая сложность - **НЕТ**. Если LOB сопадет с бакетом, который уже заполнен, то создается еще один бакет. И ссылка на него будет записана в поле `overflow` структуры бакета. В худшем случае, получим O(N).
## Алгоритм очистки
- приравнять nil ([GC](5.%20GC.md) освободит через время)
- в цикле вызвать `delete(key, value)` ([GC](5.%20GC.md) не освободит)
- вызвать `clear(map)` ([GC](5.%20GC.md) не освободит)
```go
package main

import "fmt"

func main() {
	// remove all elements
	first := map[int]int{1: 1, 2: 2, 3: 3}
	first = nil
	fmt.Println(first, " : ", len(first))

	// keep allocated memory
	second := map[int]int{1: 1, 2: 2, 3: 3}
	for key := range second {
		delete(second, key)
	}
	fmt.Println(second, " : ", len(second))

	// keep allocated memory
	third := map[int]int{1: 1, 2: 2, 3: 3}
	clear(third)
	fmt.Println(third, " : ", len(third))
}
```
## Float как ключ
Float в качестве ключа не рекомендуется из-за особенностей представления чисел с плавающей запятой. При сложении больших float, можно получить NAN. Но NAN не равно NAN.
```go
package main

import "fmt"

func main() {

  // declare map with float based key
  m := make(map[float32]struct{})

  // write two different key
  m[999999999999999999999999999] = struct{}{}
  m[999999999999999999999999998] = struct{}{}

  // check len and see one but not two keys
  fmt.Println("keys count:", len(m)) // keys count: 1
}
```

Работает даже с маленькими числами:
```go
package main

import "fmt"

func main() {
  var val1 float32 = 0.3
  var val2 float32 = 0.6

  // declare map with float based key
  m := make(map[float32]struct{})

  m[val1+val2] = struct{}{}

  var result float32 = 0.9
  _, ok := m[result]
  
  fmt.Println(ok) // false
}
```
1. Финансы лучше хранить в атомарных единицах валюты (Рубль - копейка, Доллар - цент), чтобы число было целочисленным.
2. Можно хранить как int: выделить 6 байт под рубли и 2 байта под копейки
## [any](interface#Empty%20interface%20(any)) как ключ
Нужно помнить, что есть [1.2 uncomparable types](1.2%20uncomparable%20types.md) типы, для которых не определен оператор `==` и функция хэширования.
Напомним, что тип [slice не comparable](slice#Slice%20is%20not%20comparable%20(cant%20use%20as%20key%20in%20map)). Но он удовлетворяет типу `any (пустой интерфейс)`. На этапе компиляции мы не узнаем об ошибке. 
Но в рантайме, при использовании слайса как ключа в мапе, произойдет [паника](2.1%20panic%20и%20recover.md#panic>).
```go
package main

func main() {
	var data []int
	dictionary := make(map[interface{}]struct{})
	dictionary[data] = struct{}{} // panic: hash of unshashable type []int
}
```
## Map in not comparable
По аналогии со [slice](slice.md), мапа тоже является [несравниваемой](1.2%20uncomparable%20types.md).
1. Динамическая природа мапы: это динамические коллекции, которые могут увеличиваться и уменьшаться по мере добавления и удаления пар ключ-значение.
2. Внутренняя реализация: внутр  реализация мапы включает в себя хеширование и бакеты. Распределение пар ключ-значение по этим ведрам может меняться, даже если две карты содержат одинаковые пары ключ-значение. 
3. Рандом порядок: порядок итераций по ключам карт в Go намеренно рандомизирован.
4. Мутабельность
Проблемы с эффективностью: Сравнение карт элемент за элементом потребует больших вычислительных затрат, особенно для больших карт. Реализация функции сравнения потребует перебора всех пар ключ-значение и обеспечения того, чтобы обе карты содержали одинаковые пары, что может оказаться неэффективным.
## Эвакуация
Нельзя получить указатель на элемент мапы из-за эвакуации. Может произойти, что элемент переехал и ссылка становится невалидной.

Когда средняя заполненность бакетов становится 6.5 (80%), происходит эвакуация данных - создание новых бакетов.
- Во время эвакуации, мапа держит 2 указателя на 2 массива бакетов: `buckets` и `old_buckets`.
- Массив `buckets` увеличивается в два раза.
- Работает через воркеров.
- Во время записи/удаления можете перераспределиться несколько бакетов.
- Рехеширование необходимо, когда коэффициент загрузки (количество элементов по отношению к количеству бакетов) превышает определенный порог, что приводит к изменению размера карты.
- По мере увеличения количества элементов в мапе может увеличиваться число коллизий (когда разные ключи хэшируются в один и тот же бакет), что приводит к снижению производительности. 
- Постепенное копирование: Вместо того чтобы копировать все элементы сразу, Go использует инкрементный подход: элементы перемещаются частями по мере появления новых вставок и удалений. 
## If key/value size > 128 byte
Если ключ или значение карты превышает 128 байт, автоматически сохраняется указатель на значение, а не хранится в бакете.
Но для массивов размером ровно 128 байт Go сохраняет их в бакете — что приводит к раздуванию, которое мы наблюдали.

# New(Swiss, after 1.24)
## Set performance loss
[Source](https://rushter.com/blog/go-and-hashmaps/)
[Issue](https://github.com/golang/go/issues/71368) 

В go нет «родного» типа «множество» (set). Bместо него `map[T]struct{}`:
```go
set := make(map[string]struct{})
set["apple"] = struct{}{}
if _, exists := set["apple"]; exists {
  fmt.Println("✓ apple")
}
```

Прелесть использования [struct#Пустая структура](struct#Пустая%20структура.md) в том, что у такой карты значения буквально занимают 0 байт.

В Go 1.24 `map[T]struct{}` теперь занимает ровно столько же памяти, сколько и `map[T]bool`. На значениях больше не сэкономить.

В старых картах значения хранились отдельно от ключей: в каждом бакете сначала все ключи, потом все значения:
```
[K1, K2... K8] [V1, V2... V8]
```
Компилятор видел struct{}, и не выделял под значения память.

В новых картах ключи и значения объединены в одну структуру (слот):
```
[ {K1, V1}, {K2, V2}, ... ]
```
Внутри слот выглядит так:
```go
struct {
  key  keyType
  elem elemType
}
```
По правилам компилятора, если структура заканчивается полем нулевого размера, этому полю все равно выделяется 1 байт (на случай, если какой-нибудь злодей создаст на него указатель).

А фикс-то знаете какой? Просто поменять местами key и elem 😁
```go
struct {
  elem elemType
  key keyType
}
```
Так последнее поле будет не нулевое, так что если ключ 8 байт, то и вся структура тоже 8 байт.

Таким образом, поле elem типа struct{} будет занимать 1 байт — точно так же, как bool. А весь слот — аж 16 байт, из-за [struct#Padding](struct#Padding.md).
